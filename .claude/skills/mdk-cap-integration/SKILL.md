# CAP Backend + MDK Mobile Frontend Integration

How to build a full-stack app where a CAP service provides the OData backend
and MDK provides the mobile frontend.

---

## Project structure

```
my-app/
  db/                        ← CDS data model
  srv/                       ← CAP service + handlers
  app/
    myapp_mdk/               ← MDK mobile app (generated by mdk_create)
      .project.json
      .service.metadata      ← links MDK to Mobile Services destination
      SampleApp/
        Pages/
        Actions/
        Rules/
        Services/
        i18n/
  package.json               ← CAP project root
  mta.yaml                   ← includes both CAP srv and MDK deployment
```

---

## Step 1 — Build the CAP service first

```bash
# Standard CAP service with OData V4
cds add hana --for production
cds add xsuaa --for production
```

Expose entities the MDK app needs:
```cds
// srv/cat-service.cds
service CatalogService @(path: '/catalog') {
  entity WorkOrders as projection on db.WorkOrders
    @(restrict: [{ grant: '*', to: 'MobileUser' }]);
  entity Equipment  as projection on db.Equipment
    @(restrict: [{ grant: 'READ', to: 'MobileUser' }]);
}
```

---

## Step 2 — Register CAP service as Mobile Services destination

In SAP BTP Cockpit or via `mcp__intent2app__mdk_mobile_services`:

```
Destination name:    WorkOrderService
Destination type:    Mobile Connectivity
Endpoint:            https://<your-cap-srv-url>/catalog
SSO method:          OAuth2SAMLBearerAssertion
Roles required:      MobileUser
```

Or for local development:
```
Endpoint:            http://localhost:4004/catalog
SSO method:          NoSSO (dev only)
```

---

## Step 3 — Fetch .service.metadata from CAP service

```
mcp__intent2app__mdk_mobile_services {
  "operation":      "fetch-metadata",
  "folderRootPath": "./app/myapp_mdk",
  "appId":          "com.company.myapp",
  "destination":    "WorkOrderService"
}
```

This fetches the CAP OData EDMX and saves `.service.metadata` with the entity types
defined in your CDS model.

---

## Step 4 — Scaffold MDK from CAP entities

```
mcp__mdk__mdk-create {
  "folderRootPath":  "./app/myapp_mdk",
  "scope":           "project",
  "templateType":    "crud",
  "oDataEntitySets": "WorkOrders,Equipment",
  "offline":         false
}
```

Entity sets match exactly what you defined in the CAP service projection.

---

## Step 5 — Handle XSUAA auth in MDK

MDK uses the Mobile Services OAuth flow — it does NOT call XSUAA directly.
Mobile Services acts as the auth proxy between MDK client and CAP service.

Configure in Mobile Services → your app → Security:
```
Security type: XSUAA
xs-app.json:   { "authenticationMethod": "route" }
```

In CAP xs-security.json — add Mobile User role:
```json
{
  "role-templates": [{
    "name": "MobileUser",
    "description": "Mobile app user",
    "scope-references": ["$XSAPPNAME.MobileAccess"]
  }],
  "scopes": [{
    "name": "$XSAPPNAME.MobileAccess",
    "description": "Access from MDK mobile app"
  }]
}
```

---

## Step 6 — mta.yaml — deploy both together

```yaml
modules:
  # CAP backend
  - name: myapp-srv
    type: nodejs
    path: gen/srv

  # MDK mobile app
  - name: myapp-mdk
    type: com.sap.application.content
    path: app/myapp_mdk
    requires:
      - name: myapp-mobile-services
        parameters:
          content-target: true

resources:
  - name: myapp-mobile-services
    type: org.cloudfoundry.managed-service
    parameters:
      service: mobile-services
      service-plan: standard
```

## Key differences vs pure MDK (Mobile Services OData only)

| Aspect | Pure MDK | CAP + MDK |
|---|---|---|
| OData source | External S/4HANA or sample | Your own CAP service |
| Auth | Mobile Services SSO | XSUAA via Mobile Services proxy |
| Schema changes | Must refetch .service.metadata | Redeploy CAP + refetch metadata |
| Offline | Works out of the box | Requires CAP to support delta tokens or polling |
| Local dev | Use ESPM sample | `cds watch` + MDK pointing to localhost:4004 |
